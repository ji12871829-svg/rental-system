# Deploying RPMS to Render + Neon (free tiers)

This runbook puts the whole app — API **and** built frontend — into one Render
Web Service, backed by a Neon Postgres database. Same origin, no CORS, HTTPS
included. Estimated time: 20–30 minutes.

```
Render Web Service (free)          Neon Postgres (free)
├── Node process                   ├── pooled endpoint (sslmode=require)
│   ├── Express API at /api/*      └── scales to zero when idle (cold ~500 ms)
│   └── serves frontend/dist       └── 0.5 GB storage, branch on demand
└── https://rpms-xxxx.onrender.com
```

## 0. Prerequisites

- Code pushed to a GitHub/GitLab repo (Render deploys from git; there is no
  meaningful CLI deploy). **Do not commit `backend/.env`** — secrets live in
  Render's dashboard.
- A Neon account (https://neon.tech, GitHub login works).
- The repo's `render.yaml` blueprint (added in this change) — optional but
  recommended; it pre-fills build/start commands and most env vars.

## 1. Create the Neon database

1. Neon console → **Create project**. Name it `rpms`, pick the region closest
   to your users (e.g. AWS `eu-central-1` for Kenya/EU latency).
2. On the project **Dashboard**, find the connection string. **Choose the
   *pooled* connection** (channel binding toggle OFF, `sslmode=require`
   included). It looks like:

   ```
   postgresql://neondb_owner:AbCdEf…@ep-cool-name-a1b2c3d4-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require
   ```

   The pooled endpoint routes through Neon's PgBouncer — mandatory here,
   because the app opens a small pool per instance and Render free instances
   restart often (open connections would otherwise linger until GC).
3. Optional but recommended: create a dedicated database `rpms` (Sidebar →
   Databases → New) instead of using the default `neondb`.
4. Copy the string somewhere safe — it contains the password.

### 1a. Apply the schema to Neon (optional — automatic on first boot)

From your machine (the repo is already set up for this):

```bash
# One-off: point the local tooling at Neon
export DATABASE_URL="postgresql://…-pooler…?sslmode=require"   # Windows: set DATABASE_URL=…

cd backend
npm run db:setup        # applies database/schema.sql + seed, creates default users
```

`db:setup` is idempotent (schema uses `IF NOT EXISTS`, users upsert), so it is
safe to re-run. **You can skip this entire step** — on the first Render boot
the app detects the empty database and applies schema + seed + default users
itself (`src/db/bootstrap.ts`, awaited before the health check turns green).

**First production decision (either way):** the seed creates three sample
users with known passwords (`admin@rpms.local` / `Admin@2026!` etc.). Log in,
change those passwords immediately (Users page), and delete any sample tenants
or payments you don't want in production.

Verify from the same shell that the schema landed:

```bash
npx tsx -e "import {pool} from './src/config/db'; pool.query('select count(*) from units').then(r => {console.log('units:', r.rows[0].count); return pool.end();})"
```

## 2. Create the Render Web Service

1. Render Dashboard → **New → Blueprint** → pick this repo. Render reads
   `render.yaml` and shows the service; fill in the prompted variables:
   - `DATABASE_URL` — the Neon **pooled** string from step 1.
   - `JWT_SECRET` — auto-generated by the blueprint (`generateValue: true`);
     keep whatever it produces.
2. No blueprint? Create **New → Web Service** instead and set:

   | Setting | Value |
   |---|---|
   | Runtime | Node |
   | Build command | `cd frontend && npm ci && npm run build && cd ../backend && npm ci && npm run build` |
   | Start command | `npm run start --prefix backend` |
   | Health check path | `/api/health` |

3. Add environment variables (dashboard → Environment):

   | Key | Value | Notes |
   |---|---|---|
   | `NODE_ENV` | `production` | enables prod cookie/SSL behavior + static serving |
   | `DATABASE_URL` | Neon pooled URL | `?sslmode=require` included |
   | `JWT_SECRET` | long random string | **required in prod** — app refuses to trust the dev fallback |
   | `SMS_PROVIDER` | `mock` | start safe; switch to `africastalking` when ready |
   | `EMAIL_PROVIDER` | `mock` | same |
   | `BUSINESS_NAME`, `BUSINESS_REG_NO`, `BUSINESS_PHONE`, `BUSINESS_EMAIL` | your details | appended to receipt SMS + legal pages (also editable later in Settings) |

   **Do not set `PORT`** — Render injects it and the app reads it.
   **Do not set `CORS_ORIGIN`** — same-origin deploy, CORS never fires. (Only
   needed if you later split the frontend to a different domain.)

4. **Deploy.** First build takes ~4–6 minutes (installs both workspaces,
   builds the Vite frontend, compiles the API). Watch the log for:
   `RPMS API listening on http://localhost:10000 (production)`.

   Before the API boots, a **predeploy gate** (`backend/scripts/predeploy-check.mjs`,
   wired into `npm start`) verifies `DATABASE_URL`/`JWT_SECRET` are set, the
   database is reachable **and has the schema** (`npm run db:setup` was run —
   §1a), and warns about unfilled `BUSINESS_*` identity vars. A failed gate
   marks the deploy bad and keeps the previous release serving.

## 3. Verify

- `https://<your-service>.onrender.com/api/health` → `{"status":"ok", …}` —
  the `config` block tells you at a glance which env knobs are still unset
  (`jwtSecretSet`, `businessNameSet`, …).
- Open the root URL → the RPMS login screen renders. Log in with the seed
  admin, then **change the password**.
- Deep-link check: paste `https://…/tenants` in a fresh tab — the SPA fallback
  should render the tenants page, not a 404.
- Offline/PWA: the service worker registers on second load; the app installs.

## 4. Go-live checklist (before real money flows)

1. **Seed users** — change all three default passwords, disable accounts you
   don't need (Users page).
2. **Branding** — Settings page: fill legal name, registration number, phones,
   emails. Every legal page, receipt and SMS pulls from here.
3. **SMS** — set `SMS_PROVIDER=africastalking` + `SMS_USERNAME`/`SMS_API_KEY`,
   register the delivery-report callback in the AT dashboard:
   `https://<your-service>.onrender.com/api/sms/delivery-reports`
   (AT requires an HTTPS endpoint — Render gives you one for free).
   Optionally set `SMS_LOW_BALANCE_THRESHOLD`.
4. **Email** — set `EMAIL_PROVIDER=smtp` + `SMTP_*` + `EMAIL_FROM` when you
   want emailed receipts/letters to actually send.
5. **Backups** — Neon free tier does not include scheduled backups. Until you
   upgrade, take manual exports: Neon console → **Backup & restore** → or
   `pg_dump "$DATABASE_URL" > backup-$(date +%F).sql` from a cron machine.
   Monthly is fine at this scale; weekly is better.
6. **Cold starts** — the free Render instance sleeps after ~15 min idle; the
   first request then takes ~30–60 s while it boots. The frontend shows the
   loading state; staff just see a slow first page. If that annoys anyone,
   a monitor pinging `/api/health` every 10 min keeps it warm (defeats the
   purpose of free, but works). Neon also scales to zero (~500 ms cold DB).

## 5. Daily operations

| Task | How |
|---|---|
| Deploy an update | push to the default branch — Render auto-deploys (`autoDeploy: true`) |
| Roll back | Render dashboard → the bad deploy → **Roll back** |
| See API logs | Render dashboard → Logs tab (stdout/stderr) |
| Inspect the DB | Neon console → SQL Editor (or `psql "$DATABASE_URL"`) |
| Rotate JWT_SECRET | dashboard env change → redeploy (logs everyone out) |
| Change branding | in-app Settings page — no redeploy needed |

## 6. Known trade-offs of the free tier

- **Sleeps**: explained above. Upgrading Render to Starter ($7/mo) removes it.
- **0.5 GB Neon storage**: years of receipts/PDFs/audit rows for one property
  fit easily; email attachments are stored base64 in `email_notifications`,
  which grows fastest — the retention sweep keeps tenant data trimmed, but
  consider periodically archiving old email rows.
- **No custom domain on Render free** — the `onrender.com` URL stays. Custom
  domains need at least the paid tier. Fine for internal use.
- **Bandwidth 100 GB/mo** — orders of magnitude above this app's usage.

## 7. If something breaks

| Symptom | Cause | Fix |
|---|---|---|
| Health check fails, log shows `Could not connect to PostgreSQL` | Wrong/unreachable `DATABASE_URL` | Re-paste the **pooled** Neon URL, keep `?sslmode=require` |
| Login returns 401 for every user | Seed users never created and bootstrap didn't run | Check boot logs for `[bootstrap]` lines; if absent, re-run `npm run db:setup` locally with `DATABASE_URL` pointing at Neon |
| `text` fields render with `[bracketed placeholders]` | Business branding not filled | Settings page → fill identity fields |
| SMS recorded but never delivered | `SMS_PROVIDER=mock` | Set provider + credentials, redeploy |
| Emailed receipts fail | `EMAIL_PROVIDER=mock` or missing `SMTP_*` | Configure SMTP, redeploy |
| App loads but every API call 404s | Built frontend served but API routes missing → usually a stale build | Dashboard → **Manual deploy → Clear build cache & deploy** |
| Blank page after a deploy | Stale index.html referencing old hashed chunks | Hard refresh (Ctrl+Shift+R); the app also self-heals by reloading once on a failed chunk load |
